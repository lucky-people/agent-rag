## 第一部分：项目理解与动机

### Q1. 用 30 秒介绍一下你的项目

【考察点】表达逻辑：项目是什么 → 解决什么问题 → 怎么解决 → 效果如何。

**回答**：
"我做的是一个面向郑州本地租房场景的智能问答系统，核心难点是租房咨询是**异构数据 + 跨域知识**问题——房源查询是结构化数据需要精确 SQL，法律问答是非结构化知识需要语义检索加引用。所以我设计了**双引擎架构**：结构化数据走 A2A 多智能体 + MCP 工具调用链路（Text2SQL 精确查询），法律知识走 **Agentic RAG** 链路（混合检索 + Rerank + Self-RAG 反思循环），由 LLM 意图路由统一调度。整套系统在 RTX 4060 上完成了全链路量化评估：意图分类 98.28% 准确率、Rerank 选型经三层证据验证（检索质量 +45%、生产配置答案质量 +55%）、反思纠错案例 2/5 题自检拦截并全部纠错成功。项目有 41 个单元测试和完整的评估脚本，所有数据都是仓库内实际运行出来的。"

### Q2. 什么是 Agentic RAG？和朴素 RAG 有什么区别？

【考察点】是否理解 Agentic RAG 的本质（从"检索-生成"管线到"Agent 自主决策循环"）。

**回答**：
"朴素 RAG 是固定管线：检索一次 → 生成一次，检索词和策略都是写死的。Agentic RAG 的本质区别是**让 LLM 以 Agent 身份参与检索决策的闭环**。我的实现里有两个关键差异：
1. **检索规划**：不是拿用户原问题直接检索，而是 LLM 先自主决定检索词和策略（直接检索/假设问题检索/子查询检索/回溯检索），多词覆盖问题的不同侧面；
2. **反思循环（Self-RAG）**：生成答案后，LLM 作为评审员判断'答案是否被检索证据充分支持'，如果不支持，就分析缺失证据、改写检索词、重新检索再生成，最多 2 轮。

所以朴素 RAG 是'一条道走到黑'，Agentic RAG 是'发现问题 → 自我修正'。我实测的纠错案例里，Q1 押金利息首轮检索到的证据没提利息赔偿，反思判定 supported=false，改写查询后命中《民法典》584 条，引用准确性从 3 分提到 5 分——这就是 Agentic 相对朴素的价值所在。"

### Q3. 为什么需要 Agentic RAG？朴素 RAG 的痛点是什么？

【考察点】问题意识——Agentic RAG 不是炫技，是解决真实痛点。

**回答**：
"朴素 RAG 有三个我实际踩到的痛点：
1. **单次检索可能漏证据**：法律问答场景，一个问题的答案可能需要跨多个法条。我用原问题直接检索，可能只召回'押金返还'相关条文，漏掉'利息赔偿'的依据——我评估里 Q1 就出现这个情况；
2. **检索词质量不可控**：用户口语化提问（'房东拖着不退钱怎么办'）直接拿去检索，向量召回效果差；
3. **幻觉无法拦截**：LLM 可能凭训练记忆回答，引用的法条根本不在检索上下文里，没有机制发现。

Agentic RAG 让 LLM 自己规划检索词（解决痛点 2）、生成后自检证据充分性（解决痛点 3）、证据不足时改写重检（解决痛点 1）。这是我在实际评估中发现 v1 答案质量被噪声污染、引用凭空出现之后，才真正理解必须做这一层的原因。"

### Q4. 你这个项目算 Agentic RAG 吗？多智能体和 Agentic RAG 是什么关系？

【考察点】概念边界清晰度。

**回答**：
"算，而且我认为我的实现符合 Agentic RAG 的核心定义：**Agent 自主决策 + 工具调用 + 自我反思循环**。`generate_answer_agentic` 就是 Self-RAG 式实现：检索规划（Agent 决策）→ 工具化检索（调 Milvus）→ 生成 → 反思自检 → 改写重检。

多智能体和 Agentic RAG 是**两个维度**：多智能体是**横向分工**（跨域问题拆给 house/metro/poi/legal 不同 Agent 并行处理，编排器汇总），Agentic RAG 是**纵向深挖**（法律单域内的问题，Agent 反复检索-生成-反思直到证据充分）。它们通过意图路由结合：跨域复杂问题走编排，法律问题走 Agentic RAG。我 README 里把这条讲清楚，面试时也可以主动澄清，避免概念混淆。"

## 第二部分：架构与设计决策

### Q5. 为什么用双引擎架构，而不是全 RAG 或全 Text2SQL？

【考察点】技术选型的思考深度——是否理解"数据形态决定技术路线"。

**回答**：
"核心结论是**数据形态决定技术路线**。我对比过三种方案：
- 全 Text2SQL：法律条文是非结构化文本，没法精确 SQL 查询；
- 全 RAG：'金水区 2000 元以下整租房'是精确筛选条件，向量检索会给出模糊的近似结果，还容易算错租金区间；
- **双引擎**：结构化数据（房源/地铁/POI）走 Text2SQL Agent（精确、可验证、可排序），非结构化法律知识走 RAG（语义匹配 + 引用溯源），由 LLM 意图路由决定走哪条。

这个决策的代价是系统复杂度翻倍（两套链路都要维护），但换来的是两类问题的准确率都更高。我评估里 Q3 还体现了一个附加价值：FAQ 精确命中时 MySQL 直答只要 3ms，避免了不必要的 RAG 成本。"

### Q6. 为什么用 A2A 协议做多智能体编排？和 LangGraph / AutoGen 的区别？

【考察点】框架选型认知 + 对多智能体协作本质的理解。

**回答**：
"我调研过三类的方案：
- **LangGraph**：图状态机，适合流程强约束的工作流，但节点、边、状态都要显式定义，跨域动态拆解不灵活；
- **AutoGen**：ConversableAgent 对话式协作，对话轮次开销大、控制粒度粗；
- **A2A（Agent2Agent）**：Agent 间通过能力描述和任务卡片协作，**编排器模式**——RecommendAgent 作为编排器，LLM 把跨域问题拆成子任务，`asyncio.gather` 并行调度 house/poi/metro 子 Agent，各自独立返回结果，编排器汇总。

选 A2A 的关键原因是我的场景是**并行子任务**而非**串行多轮对话**，A2A 的任务卡片模型天然匹配'拆解 → 并行 → 汇总'，而且 python-a2a 库的流式消息机制能支撑前端链路追踪。"

### Q7. 意图路由为什么用 LLM + BERT 两级？

【考察点】成本/精度权衡的工程思维。

**回答**：
"两级各司其职：
- **入口 LLM 意图识别**（qwen-plus）：负责 6 类意图 + 多意图组合识别 + 子查询改写，因为多意图组合（'1号线附近2000以下+周边美食'）语义复杂，小模型做不好；
- **RAG 内部 BERT 分类器**（bert-base-chinese 微调）：只区分'通用知识/专业咨询'二分类，这是高频决策点（每次法律提问都要判），用 LLM 做成本高、延迟大，BERT 实测 **98.28% 准确率**、几乎零延迟。

这是个典型的'贵模型做复杂决策、小模型做高频简单决策'的分层思想。我还加了**规则前置兜底**：'押金''退租'等关键词强制走专业咨询，防止高风险法律问题被误分流到闲聊链路，实测兜底命中率 7/7 = 100%，专业咨询漏报率压到 0。"

### Q8. 混合检索为什么是 BM25 + 稠密 + 稀疏三路？权重怎么定的？

【考察点】对检索组件的理解深度。

**回答**：
"三路各补短板：
- **BM25**（关键词）：法律术语（'民法典''押金'）精确匹配强，但无语义；
- **BGE-M3 稠密向量**（1024 维）：语义相似召回，但可能丢术语（'退还''返还'语义相近但字面不同）；
- **BGE-M3 稀疏向量**：BGE-M3 的稀疏编码相当于学习过的'词级特征'，比 BM25 的词频统计更语义化，补充前两路。

融合用 Milvus `WeightedRanker(1.0, 0.3)`——稠密权重 1.0、稀疏 0.3。这个权重不是拍脑袋：BGE-M3 的官方实践和我的消融都表明稠密为主、稀疏辅助（稀疏向量质量依赖分词，权重过高会引入噪声）。检索后取 Top-50 候选，去重父文档，再进 Reranker 精排。评估证据：混合检索比纯稠密在检索质量评判上相关性 2.75 vs 2.12，说明稀疏路确实有增量。"

### Q9. 为什么用 BGE-M3？为什么还要加 BGE-Reranker？会不会重复？

【考察点】双阶段检索（召回 + 精排）的理解。

**回答**：
"BGE-M3 是**召回器**（bi-encoder），它的定位是'宁多勿漏'——把候选从全库缩到几十篇；BGE-Reranker 是**精排器**（cross-encoder），对候选逐对计算问题-文档的交叉注意力相关性，是**精排**——保证进入 LLM 的 Top-2 是最相关的。两者不重复：bi-encoder 提前把 query 和 doc 各自编码成向量（可缓存、可海量比对），但**丢失了 query-doc 的交互信息**；cross-encoder 做完整交互、精度高，但没法全库扫（太慢）。

这是我评估里最有意思的一个发现：**召回指标（Recall@5/MRR）测不出 Rerank 的价值**，因为候选集合相同、只是排序不同；但**生产配置 CANDIDATE_M=2 只取 Top-2 时**，排序质量直接决定答案质量，Rerank 综合分 +55%。所以 Rerank 的价值要'取前几名喂给 LLM'才能体现——这也是我评估方法论的核心洞察：**指标必须和待验证的假设对齐**。"

### Q10. 反思循环的具体实现？怎么防止死循环？

【考察点】实现细节 + 工程边界意识。

**回答**：
"实现是 `generate_answer_agentic(query, max_rounds=2)`，核心是 4 个 prompt：
1. `retrieval_plan_prompt`：LLM 输出 `{"queries": [...], "strategy": "..."}`，自主规划检索方案；
2. 检索（工具调用）：对每个检索词执行三路混合检索 + Rerank + 去重，合并候选；
3. 生成：带引用条文生成答案；
4. `reflection_prompt`：LLM 评审输出 `{"supported": true/false, "reason": "...", "missing": "..."}`，判断答案是否被证据充分支持。

**防死循环靠三把锁**：① `max_rounds=2` 硬上限，最后一轮强制输出不再反思；② 反思 prompt 明确写'不要因为证据略少就判 false，只有核心结论悬空或明显缺关键信息才判 false'，防止过度反思；③ 查询改写最多输出 2 个检索词，控制每轮成本。反思轨迹全部记录在 `last_agentic_trace`，每轮检索词/文档数/判定/缺失证据/该轮答案都可审计——实测平均 1.3 轮收敛，没有出现死循环。"

### Q11. 记忆模块怎么设计？多轮对话怎么处理？

【考察点】对话系统的基础工程能力。

**回答**：
"短期记忆和长期记忆分开：
- **短期记忆**：会话窗口，最近 5 轮格式化进 prompt（`history[-5:]`），会话 TTL 1 小时，Redis 存储，写入加锁防并发覆盖；
- **长期记忆**：MySQL 用户画像（注册信息、偏好、收藏、历史），支撑个性化推荐——比如收藏过的房源会在后续推荐里加权。

多轮对话里 Agentic RAG 的处理：历史会拼进生成 prompt 保持上下文连贯，但**检索规划只针对当前问题**（避免历史干扰检索词）。这是有意的设计取舍——法律问题的检索词应该聚焦当轮 query，历史只是生成时的参考。"

## 第三部分：评估体系（本项目最大亮点，必被深挖）

### Q12. 你怎么评估 RAG 系统？用了哪些指标？

【考察点】评估体系完整性 + 是否有自己的思考。

**回答**：
"我的评估体系覆盖**路由 → 检索 → 生成 → 缓存**全链路，五个实验：
1. **意图分类**：Accuracy / Precision / Recall / F1 / 混淆矩阵，98.28%；
2. **Rerank 选型价值**（核心）：三层证据——检索质量直接评判（LLM 对 Top-5 文档列表打分）、生产配置对比（CANDIDATE_M=2）、答案质量（评判可见上下文）；
3. **GPU 耗时**：4 策略消融 + 生产路径实测；
4. **三链路延迟**：MySQL 10.8ms / Redis 2.4ms / RAG 8908ms，加速比 825x/3700x；
5. **Agentic vs 朴素 + 反思纠错案例**：端到端对比 + 每轮反思轨迹审计。

关键设计原则：**答案质量让 LLM 独立评判（0-5），且评判时可见对应检索上下文**——这是保证评判公正性的核心，也是我 v1 评估踩过坑后修复的。"

### Q13. 为什么 Recall@5/MRR 不能作为你的主指标？

【考察点】评估方法论深度——这是最容易和别的候选人拉开差距的问题。

**回答**：
"我最初就是用 Recall@5/MRR 做消融，结果出现一个反直觉现象：**纯稠密向量和混合检索的 MRR 反而高于混合+Rerank**。我当时没有直接接受这个结果，而是逐题分析了数据，发现根因是**指标与待验证假设错位**：
1. 我的相关性判定是'词面命中 ≥2 个标注关键词'，但 Reranker 是语义相关性 cross-encoder——**词面最相关 ≠ 语义最相关**，用词面口径去测语义模型，测的根本不是同一件事；
2. Rerank 不改变候选集合（Top-50 去重后一样），只改变排序——Recall@5 这种'集合级'指标天然测不出排序价值；
3. 消融里 D 是'全量重排'（50 候选去重后 20-40 篇全排），和生产 CANDIDATE_M=2 不一致。

所以我的结论是：**评估指标必须与要验证的技术假设对齐**。验证 Rerank 要看'排序质量/进入 LLM 的上下文质量'（NDCG、Top-1 相关率、生产配置下的答案质量），而不是笼统的召回率。这个'发现指标错位 → 修复评估 → 结论翻转'的过程，本身就是评估体系设计的深度体现，我 README 里专门记录了 v1→v2 的演进。"

### Q14. 你的 LLM 评判怎么保证公正？会不会自说自话？

【考察点】对 LLM-as-Judge 局限性的认知。

**回答**：
"我做了四层防护，也诚实说明局限：
1. **评判可见上下文**：评判 prompt 里注入该答案实际使用的检索文档，让它真的去验证'引用的法条是否在上下文中'——v1 的教训就是评判 LLM 看不到上下文，只能凭答案文本猜，数据被噪声污染；
2. **检索质量与生成质量分离**：检索层让 LLM 直接对三策略的文档列表打分（相关性/支撑性），不经过生成环节，避免生成噪声污染检索结论——这是 Rerank 价值能稳定显现的关键；
3. **多次评判取均值**：答案质量每题评判 2 次取平均，抗 LLM 评判随机性；
4. **确定性指标补充**：耗时、加速比、GPU 实测都是客观数字，不依赖 LLM。

局限也承认：LLM-as-Judge 仍有偏好偏差（比如偏好更长的答案），8-30 题样本量偏小。所以我把它定位为'系统内相对比较'（三个策略同一套评判器对比），而不是绝对质量分数——相对比较下偏差对三策略是公平的。"

### Q15. D 的检索质量 4.00 明显高于 C 的 2.75，但答案质量为什么只高一点（2.35 vs 1.75）？

【考察点】数据解读能力——能否解释不完美的实验结果，这是面试官最喜欢的追问。

**回答**：
"这个差异本身是合理的，我的解读是**'生成质量受多因素影响，检索只是其一'**：
1. **Top-5 vs Top-2 口径不同**：答案质量实验喂给 LLM 的 Top-5 上下文，C 和 D 的 Top-5 集合基本一致（候选池相同，只是排序不同），LLM 把 5 篇都读进去了，顺序影响被稀释；而生产配置只取 Top-2 时，D 领先 +55%——**取前几名越少，排序的价值越放大**；
2. **LLM 生成噪声**：同一上下文两次生成答案都不同，Q5/Q6 有多策略同时低分（生成异常），拉低了均值；
3. 所以两个指标回答的是不同问题：检索质量评判证明'**Rerank 让文档更相关**'（选型正确），答案质量证明'**端到端不劣化且引用更准**'（2.19 全场最高）。面试官如果追问，我会主动讲清楚这个层次，反而体现对数据边界理解得透。"

### Q16. 样本量只有 8-30 题，你的评估结论可信吗？

【考察点】统计意识 + 诚实。

**回答**：
"我承认样本量偏小是局限，说三点：
1. **结论有结构性支撑**：D 在检索质量 8 题中 6 题领先、生产配置 4 题里 Q8 是 5/5/4 vs 0/0/3 的悬殊差异，不是靠均值凑出来的，是逐题可审计的；
2. **定位是相对比较**：三策略跑同一批题、同一评判器，系统性偏差对三者公平，相对排序可信；
3. **改进方向明确**：我已经写了数据驱动的测试集生成器，下一步计划扩到 30-50 题；也可以接 RAGAS 第三方基准做交叉验证。面试官如果追问，就如实说'当前定位是项目内选型验证，全量基准是后续工作'——比硬吹更可信。"

## 第四部分：工程与可靠性

### Q17. SQL 注入怎么防？只读白名单怎么实现？

【考察点】安全意识 + 实现细节。

**回答**：
"三层防护：
1. **MCP 工具层统一校验**：所有 SQL 执行都过 `validate_readonly_sql`，只允许 SELECT/WITH 开头，正则拦截 DROP/INSERT/UPDATE/DELETE/注释符号/分号拼接等危险模式；
2. **数量词强制 LIMIT**：`enforce_limit` 从用户语句里解析数量词（'两套'→2），强制注入 LIMIT 兜底，防止 LLM 生成的 SQL 不带 LIMIT 全表返回；
3. **连接池与最小权限**：数据库账号仅授查询权限。

实现上有个细节：校验不是拦截'看起来像注入的字符串'，而是**白名单校验'只允许查询语法'**——这是更可靠的安全模型。41 个单元测试里有专门的 SQL 白名单用例覆盖。"

### Q18. 错误四层归因是什么？为什么这么设计？

【考察点】异常处理设计思维。

**回答**：
"我给所有查询结果定义四层状态：`success` / `no_data` / `error` / `connection_error`，关键是**不同错误走不同的修复路径**：
- 连接失败（connection_error）→ 重试连接，不是重试 SQL（SQL 没毛病）；
- SQL 执行错误（error）→ LLM 修正 SQL 重查，不是重试连接；
- 空结果（no_data）→ 放宽条件重查（去掉价格区间、扩大区域），不是重跑原 SQL；
- success → 直接返回。

如果只用'成功/失败'两态，失败后只能盲目重试，既浪费 LLM 调用也大概率失败。分层后**对症下药**，这是我 README 可靠性设计里的核心条目，也是生产系统健壮性的体现。"

### Q19. Redis 缓存怎么设计？会不会有缓存污染/一致性问题？

【考察点】缓存工程细节 + 实际踩坑经验。

**回答**：
"三层缓存：BM25 语料缓存、FAQ 答案缓存、RAG 答案缓存（`rag_answer:*`）。命中 RAG 答案缓存直接返回，跳过 BM25/检索/重排/LLM 全链路，实测 2.4ms vs 8908ms。

**一致性我踩过真实坑**：评估时发现有的题耗时只有 2ms，一查是 Redis 里存了旧答案——**缓存污染会伪造假快响应**。所以我所有评估/对比脚本运行前必须清 `rag_answer:*` 键（`redis_client.delete(f"rag_answer:{query}")`），保证测的是真实全链路。这也说明：**评估系统的环境控制非常重要**，缓存是速度优化，但不能让它在评估时干扰数据真实性。生产上缓存键带版本号、会话级隔离是后续优化方向。"

### Q20. 超时梯度为什么这么设计？

【考察点】分布式系统基本素养。

**回答**：
"LLM 10s < MCP 25s < 子 Agent 30s < 编排 90s——**每层超时都大于内层**，防止内层还在跑外层就超时，造成'下层还在算、上层已经放弃了'的资源浪费；同时 90s 是编排器上限，防止极端情况无限阻塞。legal 域单独放宽到 90s，因为 Agentic RAG 有反思循环（可能 2 轮检索+生成），比其他域慢，要给足时间。这个设计保证了系统的**可用性边界**：任何环节挂掉，用户最多等 90s 拿到友好兜底回复，而不是无限转圈。"

## 第五部分：深度追问（拉开差距的问题）

### Q21. 你的反思循环和 LangChain 的 Self-RAG / Corrective RAG 有什么区别？

【考察点】对主流实现的横向对比认知（面试官确认你不是只抄了概念）。

**回答**：
"三点区别：
1. **判断依据不同**：论文 Self-RAG 用专门的 reflection token 训练模型判断，Corrective RAG 用检索相关性分数判断；我的实现让**通用 LLM 做证据充分性评审**（读上下文+答案，输出 supported/reason/missing），不需要额外训练，更工程化；
2. **纠错动作不同**：Corrective RAG 是'补检索+重写答案'，我的实现是**改写检索词重检**——针对法律场景'漏了哪条法条就补哪条'更精准；
3. **可观测性**：我把每轮反思轨迹（检索词/文档数/判定/缺失证据/该轮答案）完整落盘，前端可视化——论文实现偏研究，我的偏生产。

一句话：**我借鉴了 Self-RAG 的'自检'思想，但落地成了一套无需额外训练、可观测、可审计的工程实现**。"

### Q22. 反思判断会不会误判？怎么验证反思质量？

【考察点】对 Agent 自我评估局限性的认知。

**回答**：
"会，LLM 自评不是完美的。我做了两件事：
1. **判断标准设计**：反思 prompt 明确判定标准（核心结论是否在证据中有依据、是否遗漏问题要求的关键信息），并写了'不要因为证据略少就判 false'的校准指令，降低过度反思；
2. **实证验证**：反思纠错案例实验里，我记录了每轮判定和最终答案，用 LLM 对比'反思前 vs 反思后'的答案质量——2/5 触发反思的题，引用准确性分别 3→5、4→5，全部纠错成功；4/5 直接通过的题判定也正确（证据充分）。也就是说**该拦的拦住了、不该拦的没拦**，这是对反思质量最好的验证。后续可以引入人工抽样标注反思判定的准确率，量化这个指标。"

### Q23. 如果用户问的问题知识库里没有，怎么办？

【考察点】失败处理 + 诚实边界。

**回答**：
"三层机制：
1. **检索层**：检索不到相关内容时，混合检索会返回低相关文档，Rerank 后 Top-2 仍可能不相关——此时生成 prompt 明确要求'若上下文不足以回答，说明上下文未覆盖'，答案会诚实告知，不硬编；
2. **反思层**：Agentic 反思会判定 supported=false，改写查询再试一轮（可能换检索词能挖到）——这是 Agentic 相对朴素的一层兜底；
3. **路由层**：完全超出知识库范围的问题（比如非租房法律问题），入口 LLM 意图识别可能分流到 chat 通用对话，或 RAG 返回'建议咨询专业律师'的兜底话术。

**诚实是最重要的**：法律场景最忌讳幻觉，我 README 里强调'引用条文可溯源'，答案必须基于检索上下文，这是系统设计的第一原则。"

### Q24. Agentic RAG 一次回答要调用几次 LLM？成本怎么控制？

【考察点】成本意识（生产落地必须回答）。

**回答**：
"拆开算：检索规划 1 次 + 生成 1 次 + 反思 1 次（每轮）+ 查询改写 1 次（仅反思不通过时）。所以：
- 首轮通过：3 次（规划+生成+反思）；
- 触发反思：5 次（+改写+第二轮生成，第二轮不再反思因为 max_rounds=2）。

**成本控制四层**：
1. **Redis/MySQL 前置**：高频 FAQ 命中直答，根本不进 RAG——三链路实测 2.4ms/10.8ms vs 8908ms，大部分重复问题成本≈0；
2. **BERT 分流**：通用知识不检索不反思，零成本；
3. **max_rounds=2**：反思最多一轮，成本有上限；
4. **生产混合策略**：我 README 里明确提出'普通问题走朴素 RAG，自检不通过才升级反思重检'——这是从实验五（Agentic 10.4x 耗时）得出的工程结论，把贵的反思用在刀刃上。

面试官如果问'Agentic RAG 值不值'，我的回答是：**它值得用在证据缺失会致命的场景（法律），不适用于所有问题，所以要有路由和分级**。"

### Q25. 代码里 `last_agentic_trace` 是什么？为什么要设计它？

【考察点】是否真的自己写的代码 + 可观测性设计意识。

**回答**：
"`last_agentic_trace` 是反思循环的**完整运行轨迹**，记录 `query`、`rounds`（每轮的检索词、文档数、supported 判定、reason、missing、该轮答案）、最终引用。设计动机：
1. **可观测性**：前端链路面板要展示'反思了第几轮、为什么重检'，没有轨迹就无法可视化——这是 Agentic RAG 可解释性的关键；
2. **可审计性**：任何一次回答都能回查'它到底检了什么、判了什么、改了什么'，出问题能定位；
3. **评估数据来源**：反思纠错案例实验的 CSV/报告全部来自这个轨迹字段，我后面给每轮补了 answer 字段，让'首轮答案 vs 最终答案'可对比。

这是我 README 里'**可观测的 Agentic RAG**'落地的核心设计，也说明我不是只调 API，而是把 Agent 行为当工程对象来管理。"

### Q26. 你未来会怎么优化这个项目？

【考察点】学习能力 + 规划能力（加分题）。

**回答**：
"四个方向，按优先级：
1. **评估扩展**：测试集扩到 30-50 题 + RAGAS 第三方基准交叉验证 + 人工抽样标注，补统计显著性；
2. **反思增强**：把 LLM 自评升级为'自评 + 确定性校验'（如引用条文是否真的在上下文中做字符串/向量校验），降低误判；给反思循环加'是否值得反思'的前置判断（Query-rewriting gate），控制成本；
3. **检索增强**：HyDE（假设文档增强）、Query 分解做多跳检索，法律场景多跳问题（'A 和 B 都违约时责任怎么算'）是当前短板；
4. **工程化**：向量库分片、Embedding 缓存、流式评估（把评判也做成异步）。

我会主动说'评估先行'——先补全评估体系再动算法，避免又出现指标错位的问题。"
