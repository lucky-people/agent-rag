# 技术选型与设计决策（Technical Decisions）

> 本文档回答一个问题：**为什么这么设计？**
> 每个决策按「背景问题 → 候选方案对比 → 决策 → 理由 → 代价」结构记录，可直接作为架构设计答辩与面试的素材。

---

## 1. 为什么用 MCP 封装数据库工具，而不是 function calling？

**背景**：多智能体需要执行 SQL 查询数据库，LLM 需要一种"调用外部工具"的机制。

**候选方案对比**

| 方案 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| Function Calling | LLM 直接输出 JSON 函数参数，宿主进程解析执行 | 实现简单、延迟低 | 工具与模型强绑定；换模型要重写；多 Agent 共享工具困难 |
| **MCP（选定）** | 工具以独立服务暴露（8004-8007），通过统一协议调用 | 工具与模型解耦；多 Agent 复用；安全边界集中 | 多一层网络调用；需管理服务进程 |

**决策理由**：
1. **工具即服务**：4 个 MCP 服务独立启动、独立调试、独立升级，与模型完全解耦，换 LLM 不需要动工具层。
2. **一次实现处处生效**：SQL 只读白名单集中在 MCP 层（`validate_readonly_sql`），4 个 Agent 全部受益。
3. **错误可分层**：连接错误（`connection_error`）与 SQL 错误（`error`）在 MCP 层区分，上层才能对症处理。

**代价**：HTTP 调用增加毫秒级延迟；4 个 MCP 进程需要启动脚本统一管理。

**什么场景该用 function calling**：单模型、工具数量少、不需要独立服务化——毕设级集成可以，工程级服务化推荐 MCP。

## 2. 为什么"双引擎并列"？（结构化查询走多智能体，法律问答走 RAG）

**背景**：系统要回答两类本质不同的问题——结构化数据查询（房源/地铁/POI）和非结构化知识问答（法律/租房常识）。

**候选方案对比**

| 方案 | 思路 | 问题 |
|------|------|------|
| 全走 RAG | 把结构化数据也向量化检索 | 语义检索做不了精确筛选（价格≤2000、区域=金水） |
| 全走 Text2SQL Agent | 所有问题都生成 SQL | 法律条文没有表结构可查 |
| **双引擎按意图路由（选定）** | BERT 分流：结构化→多智能体，知识→RAG | 两套技术栈，维护成本翻倍 |

**决策理由**：**数据形态决定技术路线**。结构化数据的最优解是精确 SQL（Text2SQL Agent），非结构化文本的最优解是向量检索 + LLM 生成（RAG）。用 BERT 意图路由统一调度，让每类问题走它最合适的引擎，而不是让一个引擎勉强处理所有形态。

**代价**：维护两套链路（A2A+MCP / BM25+向量+Reranker），换来的是每类问题的"最优解"。

## 3. 为什么混合检索（BM25 + 稠密/稀疏向量 + Reranker）？

**背景**：RAG 的检索质量直接决定回答质量，单一检索策略有缺陷。

**候选方案**（均有消融实验数据支撑，见 `scripts/run_rag_ablation.py`）：

| 策略 | 特点 | 短板 |
|------|------|------|
| 纯 BM25 | 关键词精确匹配、快、可解释 | 无法语义匹配（"退租扣钱"≠"押金不退"） |
| 纯稠密向量 | 语义匹配强 | 专有名词、生僻词召回差 |
| **混合 + Reranker（选定）** | BM25 + BGE-M3 稠密/稀疏三路融合，BGE Reranker 精排 | 延迟略增 |

**决策理由**：
- BM25 对"押金""违约金"等法律术语敏感；稠密向量理解语义变体；稀疏向量补充专有名词。
- 三路结果加权融合后由 Reranker 精排，纠正粗排噪声。
- 消融实验证明混合策略 Recall@5 显著优于纯 BM25（约 +10 个百分点，详见实验图表）。

**代价**：多路检索 + 重排增加约 100ms 延迟；需同时维护 BM25 索引与向量库两套索引。

## 4. 为什么 Redis 缓存高频问答？

**背景**：租房常识问题（"押金能退吗""提前退租怎么办"）高度重复，RAG 全链路（向量检索 + Rerank + LLM）耗时明显。

**决策理由**：对归一化后的问题做精确 key 缓存——命中直接返回，跳过完整 RAG 链路，**响应快约 5 倍**。实现简单、无额外依赖，收益立竿见影。

**代价**：知识更新需要清缓存；缓存只对高频重复问题有收益（对长尾问题无效）。

## 5. 为什么 RAG 内部用 BERT 微调分类器分流，而不是每次让 LLM 判断？

**背景**：RAG 子系统需要区分两类问题——"通用知识"（租房常识、闲聊）与"专业咨询"（需要检索法律条文并引用）。这个分流是**检索链路内每一次请求都会执行的高频调用**。

> 说明：系统**入口**的多意图路由（house/poi/metro/recommend/legal/chat）由 **LLM（qwen-plus）** 完成——它需要语义理解与子查询改写能力，LLM 更合适；而 RAG **内部**的"通用知识 / 专业咨询"二分是高频、延迟敏感场景，交给本地 BERT 推理。

**候选方案对比**

| 方案 | 延迟 | 成本 | 稳定性 |
|------|------|------|--------|
| LLM Prompt 分类 | ~秒级 | 每次调用消耗 token | 输出可能不符合格式 |
| **BERT 微调（选定）** | <10ms | 几乎为零（本地推理） | 确定性强 |
| 纯关键词规则 | 极快 | 零 | 覆盖不全，难以组合 |

**决策理由**：RAG 内部分流是高频、延迟敏感、成本敏感场景，BERT 本地推理完全满足（微调 800 条样本，评估准确率 98.28%，见 `scripts/run_intent_evaluation.py` 与 `scripts/results/intent_evaluation_report.txt`）。同时用**租房常识关键词兜底**：命中关键词强制走 RAG 保引用，防止分类器误判导致高频常识问题不带法律依据。

**代价**：类别体系变更需重新标注训练；训练数据需要人工标注（800 条）。

## 6. 为什么用 A2A 协议，智能体之间如何协作？

**背景**：复杂问题（"1号线附近2000以下的房源"）横跨房源/地铁/POI 三个数据域，需要多个智能体协作。

**候选方案对比**

| 方案 | 优点 | 缺点 |
|------|------|------|
| 直接 HTTP 调用 | 简单直接 | 无标准协议、无能力协商 |
| **A2A 协议（选定）** | AgentCard 声明能力；标准任务协商；支持可观测 | 协议层有学习成本 |
| 单 Agent 大 Prompt | 无架构复杂度 | 无协作、不可扩展 |

**决策理由**：A2A 让**编排器模式（Orchestrator）**成为可能——RecommendAgent 作为编排器：LLM 拆解子任务（`_split_domains`）→ 按协议并行调用 House/Poi/Metro 子 Agent（`asyncio.gather`）→ 汇总综合推荐。每次子调用写入 `orchestration_trace`，前端链路面板实时展示，实现**多智能体可观测性**。

**代价**：python-a2a 生态较新；协议抽象需要额外学习成本。

## 7. 可靠性设计：超时 / 重试 / 降级 / 错误分层

**背景**：完整链路 Web → A2A → MCP → MySQL 有多层调用，任何一环故障都会影响用户体验。

**设计**：

| 机制 | 实现 |
|------|------|
| 超时 | A2A 调用 15s（web 层）/ 20s（编排器）；MCP 调用 15s |
| 重试 | SQL 执行错误 → LLM 修正重查（最多 3 次）；空结果 → 放宽条件重查（最多 3 次）；连接失败 → 自动重试（最多 3 次，0.5s 间隔） |
| 降级 | 子 Agent 全挂 → 编排器回退 text2sql；LLM 拆解失败 → 回退单域 house |
| 错误分层 | `success` / `no_data` / `error` / `connection_error` 四层状态码 |

**决策理由**：错误必须**分层**才能对症处理——`connection_error`（服务挂了）应该重试连接而不是浪费 LLM 调用去"修正 SQL"；`error`（SQL 写错）才值得 LLM 修正；`no_data`（确实没有）应该放宽条件而不是报错。早期版本曾把连接错误误当成 SQL 错误喂给 LLM 修正，白白烧掉 3 次 LLM 调用，后来通过状态码分层彻底解决。

**代价**：重试与降级逻辑增加代码复杂度；需要为每种失败设计用户可见的友好文案。

## 8. 为什么"并行预取"与"编排器"两套并行并存？

**背景**：组合查询有**两种形态**，需要不同的编排位置。

| 形态 | 例子 | 拆解者 | 并行位置 |
|------|------|--------|----------|
| 并列型（多意图） | "金水区房源 + 1号线 + 二七广场景点" | LLM 意图识别直接拆出多意图 | web_server 线程池预取（15s 超时，保序输出） |
| 交叉型（单意图多域） | "1号线附近2000以下、离地铁近的景点" | RecommendAgent 内 LLM 拆解 | 编排器 `asyncio.gather`（20s 超时） |

**决策理由**：并列问题由 LLM 意图识别一次拆解为多个独立意图，成本可控；交叉问题 LLM 意图层拆不动（"1号线"是房源的筛选条件而非独立查询对象），必须由编排器内 LLM 语义拆解。**并行只是底层手段，编排发生在哪一层（服务层 / Agent 层）才是本质区别**——前者是"主服务直连叶子"，后者是"编排 Agent 内部协作"，后者才是 A2A 多智能体价值的体现。

## 9. 为什么种子数据 + docker-compose？

**背景**：开源项目"clone 下来能不能跑"是决定 star 数的关键因素。

**决策**：`docker-compose.yml` 一键启动 MySQL + Redis + Milvus；`seed_data.sql` 提供演示种子数据；`start.sh` / `start.bat` 一键拉起全部服务；`config_local/` 模板 + 环境变量优先的读取策略解决密钥配置。

**代价**：维护多一份种子数据；配置模板需与真实环境保持一致。

## 附录：错误状态码设计

| 状态码 | 含义 | 来源 | 上层处理 |
|--------|------|------|----------|
| `success` | 查询成功且有数据 | MCP | 格式化输出 |
| `no_data` | 查询成功但数据库无结果 | MCP | LLM 放宽条件重查（≤3 次）→ 提示"未找到" |
| `error` | SQL 执行错误 / 白名单拒绝 | MCP | LLM 修正 SQL 重查（≤3 次）→ 返回具体错误 |
| `connection_error` | MCP 服务不可用 / 超时 | A2A getter | 自动重试（≤3 次，0.5s）→ "服务暂不可用" |
